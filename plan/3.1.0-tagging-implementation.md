# 3.1.0 phase 1 - ad tagging: touch points and implementation

Companion to `3.1.0-ad-tagging.md`, which decided *what* and *why*. This is
*where* and *in what order*. Every file below was opened and checked, not
inferred from its name.

Scope: the taxonomy, the admin surfaces that consume it, and bulk-action-by-group.
Tag-driven delivery is explicitly **out** - see §7.

## 1. Touch points

### Registers the thing

| File | Change |
|---|---|
| `includes/Core/class-plugin.php` | `register_post_type()` runs on `init` priority 5 (line 91). Taxonomy registers in the same method, immediately after `register_post_type( 'wbam-ad', $args )` at line 344, so ordering can never drift. |

Registering in the same callback rather than a new `init` listener is deliberate:
a taxonomy attached to a post type that has not registered yet silently does
nothing, and two listeners on the same hook is a race waiting to be reordered.

### Consumes it (FREE admin)

| File | Change |
|---|---|
| `includes/Admin/class-admin.php:56` | `manage_wbam-ad_posts_columns` already adds columns. The taxonomy column comes free from `show_admin_column`, but column *order* does not - it appends after Date. Reposition so it sits next to Placements, which is the column it relates to. |
| `includes/Admin/class-admin.php:74` | `restrict_manage_posts` already renders the enabled/disabled filter. Add the tag dropdown in the same callback, following that exact pattern including its `phpcs:ignore` for the nonce-less GET. |
| `includes/Admin/class-admin.php:255` | The existing filter is applied in a `pre_get_posts`-style handler. A taxonomy dropdown submitting the term **slug** under the taxonomy's own name is handled by core - no query code needed. Verify rather than assume; if core does it, write no code. |
| `includes/Admin/class-admin.php:814+` | Six `add_meta_box` calls. WordPress adds its own taxonomy box automatically; decide whether to keep it or hide it and fold tags into the existing Placements box for one coherent panel. Default: keep core's box, and revisit only if it reads badly. |

### Does NOT need changing, verified

- **`includes/Admin/class-admin.php:63-64`** - `wbam_enable` / `wbam_disable`
  bulk actions operate on selected IDs. Filtering the list changes what is
  selectable, so bulk-by-tag works with **no bulk-action code at all**. This is
  the whole reason to do the filter rather than invent a "bulk by folder" UI.
- **`includes/API/class-ads-api.php`** - the public ads route filters by enabled
  state and placement. Tags are an admin organisation concern in phase 1;
  exposing them is a phase 2 decision tied to delivery. Leave alone.
- **`includes/Core/class-abilities.php`** - surfaces `placements` on ad
  create/update. Same reasoning: adding `tags` here is API surface that phase 2
  may want shaped differently. Not now.
- **`uninstall.php`** - drops six tables and options. Terms are stored in core's
  `wp_terms` / `wp_term_taxonomy`, which WordPress does **not** clean up for a
  removed taxonomy. Add explicit term deletion (see task 6) or uninstalling
  leaves orphan rows.

## 2. Tasks, in order

Each task is independently verifiable. Do not batch them.

### Task 1 - register the taxonomy

`class-plugin.php::register_post_type()`, after the CPT call.

```
wbam_ad_tag
  hierarchical      true    // gives folder-shaped grouping
  public            false   // no archive; ads have no front-end URL
  show_ui           true
  show_admin_column true
  show_in_rest      false   // matches the CPT's own decision
  rewrite           false
  capabilities      manage_options for manage/edit/delete;
                    edit_posts for assign
```

`show_in_rest: false` mirrors `wbam-ad` itself. `tests/free/test-cpt.php` records
why the CPT stays off `/wp/v2`: the plugin serves ads through `/wbam/v1`, which
filters by enabled state, and exposing raw posts would publish disabled and
scheduled ads through a route with none of that filtering. A taxonomy on
`/wp/v2` would leak the same inventory shape.

**Verify:** `wp eval 'var_dump( taxonomy_exists("wbam_ad_tag"), is_object_in_taxonomy("wbam-ad","wbam_ad_tag") );'`

### Task 2 - tests for the contract

`tests/free/test-ad-taxonomy.php`:

- taxonomy exists and is attached to `wbam-ad`
- it is hierarchical (parent terms are the folder story)
- it is **not** on `/wp/v2`, for the same reason the CPT is not
- **an ad holds several terms at once** - the client's actual requirement, and
  the assertion a folder implementation could not pass
- a child term resolves its parent

Write these before the admin work. They are the contract; the UI is decoration.

### Task 3 - filter control on All Ads

`class-admin.php::render_status_filter()` - extend the existing callback rather
than adding a second `restrict_manage_posts` listener.

Use `wp_dropdown_categories()` with `taxonomy => wbam_ad_tag`,
`name => wbam_ad_tag`, `value_field => slug`, `show_option_all`, and
`hide_empty => false` so a freshly created term is selectable before anything
carries it.

**Verify in browser:** the dropdown lists terms; selecting one narrows the list;
the URL carries `?wbam_ad_tag=<slug>`; the count in the table header matches.

### Task 4 - confirm bulk-by-tag needs no code

With the filter applied, select-all selects the filtered set, and
`wbam_enable` / `wbam_disable` act on exactly those.

**Verify in browser, and this is the client's actual request:** tag three ads,
filter to that tag, select all, Disable, then confirm those three flipped and
nothing else did. If any untagged ad changes state, the filter is not
constraining selection and the task is not done.

### Task 5 - column placement

The `show_admin_column` column appends after Date. Reorder in the existing
`manage_wbam-ad_posts_columns` filter so it sits beside Placements.

**Verify:** header order at 1440 and 390; the column collapses like its
neighbours on narrow screens rather than forcing a horizontal scroll.

### Task 6 - uninstall cleanup

`uninstall.php` drops tables but nothing removes terms. Delete all
`wbam_ad_tag` terms and their relationships, following the existing file's
style.

**Verify:** create terms, uninstall in the Docker smoke stack, confirm
`wp_term_taxonomy` has no `wbam_ad_tag` rows left.

### Task 7 - journey

`audit/journeys/admin/03-tag-and-bulk-action-ads.md` - the full path: create a
parent and two children, tag ads across both, filter, bulk-disable, confirm
scope. Mirrors task 4 so the behaviour is re-checkable after any future change.

### Task 8 - manifest, changelog, CLAUDE.md

Manifest `taxonomies` entry, a 3.1.0 changelog block in the action-prefix format
(New / Improve / Fix / Security / Dev / Compat, padded, no emoji, no em-dashes),
and a recent-changes row.

## 3. Naming

`wbam_ad_tag`, not `wbam_ad_category`, despite being hierarchical.

The client says "tags" throughout, hierarchy is an implementation detail that
buys the folder behaviour, and the slug appears in admin URLs the client will
see. Matching their vocabulary costs nothing and avoids a rename later.

## 4. Free/Pro

All of phase 1 is **FREE**. Organising your own inventory is not a premium
concern, and phase 2 needs the taxonomy in the same plugin as the targeting
engine that would consume it - which is also Free. Pro gains nothing to do.

## 5. Risks

1. **Column ordering churn.** `show_admin_column` appends; repositioning means
   rebuilding the array. Cosmetic, caught by looking.
2. **`hide_empty` default.** Left at `true`, a newly created tag is missing from
   the filter until something carries it, which reads as a bug. Explicitly
   `false`.
3. **Capability choice.** `manage_options` to create terms, `edit_posts` to
   assign. Wrong here means either advertisers-with-edit-rights inventing
   taxonomy, or the site owner unable to tag. Assert in tests.
4. **Uninstall orphans.** Easy to forget; invisible until someone inspects the
   DB after removing the plugin.

## 6. Definition of done

- Taxonomy registered, hierarchical, attached, off `/wp/v2`.
- An ad demonstrably holds several tags.
- Filter narrows the list; bulk enable/disable acts on exactly the filtered set,
  proven by checking untagged ads did **not** change.
- Column sits beside Placements and behaves at 390px.
- Uninstall leaves no terms.
- Tests and a journey cover the above; both suites still green; local CI green.

## 7. Out of scope, deliberately

- Tag-driven ad **delivery**. Held pending the design question in
  `3.1.0-ad-tagging.md` §4 - whether tags scope a slot's candidate pool
  (`Placement_Engine`) or match page subject (`Targeting_Engine`). Building
  either before the client answers risks building the wrong one.
- Tags on the REST route and the Abilities API. Both are shaped by that same
  answer.
- Advertisers setting tags on submissions.
- Tags on videos and courses - Learnomy, not this plugin, though the vocabulary
  should be shared when it happens.
