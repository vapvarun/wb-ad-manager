## 2. Tags, not folders

The client asked for both folder organisation and multiple tags per ad. Those
contradict: a folder holds an ad in one place, and they explicitly want an ad
carrying several labels at once.

**Decision: one hierarchical taxonomy, no separate folder system.**

A hierarchical taxonomy gives folder-shaped grouping for free - "Practice Area"
as a parent with Civil, Criminal, Expert Series beneath it reads as folders in
the admin - while still allowing an ad to hold several terms. Building both means
two data models and two sets of bulk actions that will drift, which is the exact
pattern this plugin spent 3.0.0 undoing elsewhere.

Pending client confirmation (email drafted).

## 3. Phase 1 - the taxonomy (FREE)

Everything here is admin-side organisation. It changes nothing a visitor sees,
which is why it can ship independently of §4.

### Where it goes

**FREE**, next to the CPT it describes. The CPT is registered in
`includes/Core/class-plugin.php::register_post_type()`; the taxonomy registers
alongside it on the same `init` hook.

Free rather than Pro because organising your own ads is not a premium concern,
and because §4 needs it and the targeting engine that consumes it is also Free.

### Tasks

1. **Register the taxonomy.** `wbam_ad_tag`, hierarchical, attached to `wbam-ad`,
   `show_in_rest` false to match the CPT's own decision (see
   `tests/free/test-cpt.php` for why that is deliberate), `show_admin_column`
   true.

2. **Filter control on All Ads.** A dropdown in `restrict_manage_posts`, so
   "show me everything tagged Criminal" is one selection. This is what makes
   bulk-by-group work: filter, select all, apply. No new bulk-action code needed -
   the existing `wbam_enable`/`wbam_disable` operate on whatever is selected.

3. **Column + quick edit.** The taxonomy column comes from
   `show_admin_column`; quick-edit support needs the standard hook.

4. **Tests.** Taxonomy registered and attached; hierarchy works; an ad can hold
   several terms at once - that last one is the client's actual requirement and
   the thing a folder implementation would fail.

5. **Journey.** `admin/03-tag-and-bulk-action-ads.md` - tag several ads, filter
   by a tag, bulk-disable the filtered set, confirm only those changed.

### Not in phase 1

Migrating anything. There is no existing folder or tag data to move.

## 4. Phase 2 - tag-driven delivery (design first)

"Determine what ads should play based on what tags" is the item that changes what
visitors see, and it is ambiguous between two different features. It needs a
written design before code.

### The ambiguity

**Reading A - tags scope the candidate pool.** A slot is configured to draw from
a tag, so the Criminal slot only ever shows Criminal ads. This belongs in
`Placement_Engine::get_ads_for_placement()`, which already applies the site and
advertiser gates added in 3.0.0. Tag becomes a third filter on the same path.

**Reading B - tags match the page.** An ad shows on pages whose subject matches
its tags, so a Criminal ad follows Criminal content wherever it appears. This
belongs in `Targeting_Engine::should_display()`, alongside the existing
inclusion/exclusion rules in `_wbam_display_rules`.

These are not the same feature and a site could want either. The client sentence
supports both readings.

### Where each would land

The split in this codebase is already settled and should be followed: **FREE owns
the targeting engine and the rule vocabulary, PRO adds rules through hooks.**
Free's engine evaluates geo, schedule, display rules, page type, visitor
conditions and device, and exposes `wbam_should_display_ad` and
`wbam_ad_display_rules`. Pro's entire targeting module is three additions -
campaign pacing, a stronger frequency cap, role visibility - all layered on.

So either reading lands in **FREE**, and Pro extends it only if a premium
variant is wanted later.

### Interactions to resolve in the design

- **Against the 3.0.0 gates.** Site gate stops delivery; advertiser gate is
  selection-only. A tag filter has to compose with both, and the precedence has
  to be stated rather than emergent.
- **Untagged ads.** Do they match everything, or nothing? Getting this wrong
  either silences every existing ad on upgrade or makes tags meaningless. The
  3.0.0 placement gates chose "empty means all" precisely for upgrade safety;
  the same logic likely applies.
- **Several matching tags.** Does an ad matching three tags outrank one matching
  a single tag, or is rotation unchanged? This touches Pro's Rotation module.
- **Reporting.** If an ad is skipped for a tag mismatch, that has to be visible
  somewhere, or "why isn't my ad showing" becomes a support ticket.

## 5. Sequencing

Phase 1 ships alone and is useful alone: the client gets multi-tag ads, grouping,
filtering and bulk actions by group. Phase 2 waits on the design answer and on
client confirmation of which reading they meant.

Do not start phase 2 before that answer. Guessing between reading A and reading B
produces a feature that has to be rebuilt.
