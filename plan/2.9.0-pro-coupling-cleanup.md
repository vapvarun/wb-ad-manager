# WB Ads Rotator (FREE) 2.9.0 — Pro Coupling Cleanup

**Created**: 2026-04-29
**Sprint**: 2.9.0
**Plugin**: wb-ads-rotator-with-split-test
**Companion plan**: `wb-ad-manager-pro/plan/1.6.0-architecture-hardening.md`

---

## Why this sprint exists

We audited the Free/Pro coupling and found that FREE has a few visible issues affecting customers — broken admin links and references to PRO files that ship only with the paid plugin. We also found that FREE owns the `wbam-lucide` icon font but doesn't register it early enough, forcing PRO to register a duplicate copy.

This sprint fixes the FREE side of the architecture cleanup. PRO 1.6.0 ships in parallel.

---

## Customer impact (the only metric that matters)

| Customer expectation | Today's reality | Fix in 2.9.0 |
|---|---|---|
| "Links in Help Docs go where the label says." | Free-only customers see `Pro Settings → Modules` link → 404 | Hide Pro-area links when Pro not installed |
| "When I update Free, my icons keep working." | After Free updates lucide, PRO might still load old version | Free registers lucide on `init@1` so it's the canonical version |
| "I can read the source comments and they make sense." | 3 files reference `wb-ad-manager-pro/docs/...` (PRO paths in FREE comments) | Strip cross-plugin path references from comments |

If a fix doesn't trace back to a customer expectation, we don't ship it.

## Issues, by customer-visible severity

### 🟢 P3 — RESOLVED (false positive in initial audit)

#### Issue 6 — Help docs Pro-area links

**Status: NO CODE CHANGE NEEDED.** Verification on 2026-04-29 confirmed both `wbam-pro-settings` links in `class-help-docs.php` (lines 232 and 621) are correctly gated by `if ( $this->is_pro_active )` blocks at lines 153 (inverted: `if ( ! $this->is_pro_active )` with else branch at 196 containing line 232) and 604 (containing line 621). Free-only installs do not see these links.

**What we did instead — prevention layer:** Add a CI sniff that fails any future PR introducing a Pro-area admin URL in FREE without nearby `is_pro_active` (or `defined('WBAM_PRO_VERSION')`) check. This is documented in `wb-ad-manager-pro/plan/free-pro-architecture-contract.md` Part A §1 enforcement section.

**Original audit claim (incorrect):**

**Root cause (verified):**
- `includes/Admin/class-help-docs.php:50` — `$this->is_pro_active = defined( 'WBAM_PRO_VERSION' );`
- The "What's in PRO" teaser block at `:459` IS gated correctly with `is_pro_active` check.
- BUT lines 232 and 621 are inside the `<?php else : ?>` (free-only) branch and contain hard-coded admin URLs to `wbam-pro-settings`. They render exactly when PRO is NOT installed, so the links 404.

**Anti-pattern:**
- ❌ Patch: catch 404 with a redirect. Hides the symptom, doesn't fix that the link should never have been shown.
- ❌ Patch: install PRO settings page from FREE. Coupling violation.
- ❌ Patch: just remove the link text. Loses the educational value for free customers thinking about upgrading.

**Long-term fix:**

Two-state rendering:

1. **When PRO is active**: link to the actual PRO admin page (current behavior — line 232 is fine when PRO is loaded).
2. **When PRO is NOT active**: render as plain text describing what the feature does, with a single anchor pointing to the upgrade page (`?page=wbam-upgrade`) instead.

Code change (lines 217-235 in `class-help-docs.php`):
```php
<?php if ( $this->is_pro_active ) : ?>
    <li><?php
        printf(
            esc_html__( 'Turn modules on or off in %1$sPro Settings → Modules%2$s ...', 'wb-ads-rotator-with-split-test' ),
            '<a href="' . esc_url( admin_url( 'edit.php?post_type=wbam-ad&page=wbam-pro-settings&tab=modules' ) ) . '">',
            '</a>'
        );
    ?></li>
<?php else : ?>
    <li><?php esc_html_e( 'When PRO is active, you can turn modules on or off in Pro Settings → Modules ...', 'wb-ads-rotator-with-split-test' ); ?></li>
<?php endif; ?>
```

Same pattern for line 621 (Advertiser Dashboard FAQ).

**Why this is 5-year stable:**
- One branch per state — no implicit assumptions about Pro presence.
- Works whether PRO is installed, deactivated, or never installed.
- Future PRO admin pages change URL → only update the `is_pro_active` branch.
- Customer-visible: links go where they say. No 404s.

**Verification (browser):**
1. **Free-only install** (PRO deactivated): open Help Docs → "Pro-only admin areas" section. Verify no clickable link to `wbam-pro-settings`. Verify educational text reads clearly.
2. **PRO active**: open Help Docs → "Pro-only admin areas" section. Click "Pro Settings → Modules" link. Verify it lands on the working modules tab.
3. **PRO active, Advertiser Dashboard FAQ**: click the "Pro Settings > Pages" link. Verify it lands on the working pages tab.
4. **Free-only, Advertiser Dashboard FAQ**: verify the link is replaced with plain text or points to upgrade page.

**Prevention:**
- Add a code review checklist item: "Any link to a `wbam-pro-*` admin URL in FREE files MUST be wrapped in `if ( $this->is_pro_active )` (or equivalent)."
- Optional: phpcs sniff that flags `?page=wbam-pro-` strings in FREE without nearby `is_pro_active` / `defined('WBAM_PRO')` check.

### 🟠 P1 — Asset version skew when FREE updates lucide

#### Issue 1 (FREE side) — Move lucide registration to early init so FREE owns it definitively

**Customer experience risk:**
- We update FREE's lucide version (security patch / new icons).
- On PRO+FREE sites: PRO's advertiser portal page might enqueue `wbam-lucide` before FREE's `wbam_register_lucide()` ran (since PRO module hooks fire on `wp_enqueue_scripts`, FREE registers lazily on first ad render).
- PRO's `wp_script_is('wbam-lucide', 'registered')` returns false → PRO registers its own (older) lucide copy.
- Customer's icons render with old lucide → broken icons or missing new ones after update.

**Root cause (verified):**
- `includes/functions-ad-formats.php:82-104` — `wbam_register_lucide()` runs on `wp_enqueue_scripts` and `admin_enqueue_scripts`. Lazy registration.
- `includes/functions-ad-formats.php:112` — hooked at `wp_enqueue_scripts` priority 5 (early but not earliest).
- PRO's `class-advertiser-shortcodes.php:222-231` — registers its own copy if FREE's hasn't run yet.

**Anti-pattern:**
- ❌ Patch: tell PRO to never register lucide. Breaks if PRO is ever standalone or if FREE's hook misses an admin context.
- ❌ Patch: register lucide globally with `init@-999`. Wastes script registry slots on every page even when no ads render.

**Long-term fix:**

FREE registers lucide on `init` (priority 1) — early enough that any subsequent enqueue from any plugin/theme finds it. The cost is one row in the WP script registry (~50 bytes), which is negligible compared to the support burden of icon-font version skew.

Code change in `includes/functions-ad-formats.php`:
```php
// OLD: lazy on wp_enqueue_scripts (priority 5):
add_action( 'wp_enqueue_scripts', 'wbam_register_lucide', 5 );

// NEW: register early on init, available everywhere:
add_action( 'init', 'wbam_register_lucide', 1 );
```

Then PRO 1.6.0 deletes its registration block (`class-advertiser-shortcodes.php:220-231`) and only enqueues. Documented in `wb-ad-manager-pro/plan/1.6.0-architecture-hardening.md` (Issue 1).

**Why this is 5-year stable:**
- Single source of truth: FREE owns `wbam-lucide` registration. PRO never re-registers.
- Future replacement (e.g., switch from lucide to Heroicons): change one place in FREE.
- Customer-visible: icons update with FREE — no version skew.

**Verification:**
1. Browser: load any admin page → DevTools console → `wp.scripts.registered['wbam-lucide']` should exist before any ad renders.
2. Browser with PRO active: load advertiser portal page → DevTools Network → lucide JS loads from FREE's URL (not PRO's).
3. Bump FREE's lucide version in source → activate update → verify new version loads on both FREE and PRO pages.
4. Deactivate PRO → reactivate → no duplicate registration warning in error log.

**Prevention:**
- Add to `audit/FEATURE_AUDIT.md` under "Frontend assets": "FREE owns `wbam-lucide`. PRO consumes via enqueue only — see `plan/2.9.0-pro-coupling-cleanup.md`."
- CI check (in PRO sprint): PRO must not register `wbam-lucide`.

### 🟢 P3 — Comment hygiene (no customer impact)

#### Issue 7 — 3 FREE files have phpdoc references to PRO docs paths

**Why this matters at all:**
- Comments in `class-field-tooltips.php:11`, `class-list-empty-states.php:11`, `class-first-install-pointers.php:11` all read:
  > `(wb-ad-manager-pro/docs/superpowers/plans/2026-04-15-format-aware-placement-matching.md).`
- Customer never reads these. But future FREE-only contributors (or WP.org reviewers reading the plugin) can't follow the reference. Bad smell.

**Anti-pattern:**
- ❌ Leave it. Stale forever.
- ❌ Bundle the PRO doc into FREE. Ships PRO-internal content.

**Long-term fix:**

Strip the cross-plugin reference. If the doc context is genuinely needed, copy the relevant excerpt inline as a normal phpdoc paragraph. Otherwise just remove the line.

```php
// BEFORE:
 * The plan is documented in
 * (wb-ad-manager-pro/docs/superpowers/plans/2026-04-15-format-aware-placement-matching.md).

// AFTER (preferred — inline what you need):
 * Format-aware placement matching: each placement declares the ad formats it
 * accepts (image, code, etc.) and the engine filters candidates by fitness.
 * See `class-placement-format-map.php` for the mapping registry.

// OR (if context isn't needed):
// (delete the cross-reference paragraph)
```

**Why this is 5-year stable:**
- FREE source is self-contained.
- WP.org reviewers can read FREE's source without paywall.
- Future contributors don't chase dead links.

**Verification:**
- `grep -rn "wb-ad-manager-pro/docs" wb-ads-rotator-with-split-test/includes/` returns 0 results after fix.

**Prevention:**
- CI sniff (custom phpcs rule): FREE must not contain string `wb-ad-manager-pro/` anywhere except in the upgrade-page promo URL.
