# 3.1.0 - ad organisation, as a product feature

Supersedes the client-shaped framing in `3.1.0-ad-tagging.md` and
`3.1.0-tagging-implementation.md`. This plugin is generally available; one
client's list is the trigger, not the specification. What follows is designed
for the median site owner, and happens to satisfy the client request as a
consequence.

## 1. The real problem, for every site owner

The plugin manages ads as a CPT with placements. That works at ten ads. It does
not work at a hundred, and the failure is not dramatic - it is that the All Ads
screen becomes a wall, and every routine act becomes manual.

What a site owner cannot do today, at any scale:

- **Find** the ads belonging to one sponsor, one season, one section.
- **Act on a set.** A sponsor's contract lapses; every ad of theirs must stop.
  Today: locate them by memory, tick them individually, hope none was missed.
- **Answer "how did that group perform".** Analytics reports per ad. Nobody
  sells advertising per ad; they sell it per sponsor or per package.
- **Delegate.** An editor cannot be told "manage the Sponsors ads" because there
  is no such thing as *the Sponsors ads*.

The plugin already has this shape everywhere else - placements are grouped,
campaigns group ads for billing, packages group placements for sale. Ads
themselves are the one thing with no grouping at all.

That is the gap. Multi-tag support is the mechanism; it is not the requirement.

## 2. Why a taxonomy, and why one

**Not folders.** Folders are single-membership. A sponsor's ad is also a
seasonal ad and also a leaderboard ad. Any real inventory is multi-dimensional,
and a folder tree forces the owner to pick one dimension and lose the rest.

**Not ad-hoc meta.** A `_wbam_group` string would need its own storage, its own
filter UI, its own admin screen for renaming, and would be invisible to WP's
exporter, WP-CLI, and every developer who already knows `tax_query`. WordPress
has this primitive; not using it is work in exchange for less.

**One taxonomy, hierarchical.** Hierarchy gives the folder-shaped grouping
people ask for - a parent with children reads as a folder in the admin - while
still allowing an ad to sit in several. Two taxonomies (structural + ad hoc)
doubles the UI for a dimension most sites will not use; it can be added later
without migration if demand appears, and cannot be removed once shipped.

**Verified not to duplicate anything.** `Placement::get_group()` labels *slots*
in the picker ("WordPress", "BuddyPress") and has nothing to do with ads. Pro's
Rotation module rotates whatever set a placement returns and is configured
per-placement. Neither is an ad-grouping concept, so this collides with nothing.

## 3. Naming - a product decision

Recommendation: **`wbam_ad_category`, labelled "Ad Categories"**.

WordPress users already know categories: hierarchical, and a post can hold
several. That is exactly the behaviour wanted, under a name that needs no
explanation. "Tags" in WordPress means flat and non-hierarchical, so calling a
hierarchical taxonomy "tags" teaches the user something untrue about it.

The requesting client says "tags", but they described the *behaviour* - several
labels on one ad, grouped - which categories provide. If the label matters to a
specific site, it is one filter away.

The slug ships in admin URLs and in `tax_query` written by third parties, so it
is effectively permanent. Worth deciding once.

## 4. Scope, staged by who benefits

### Stage 1 - organisation (FREE)

Every site owner benefits, at any scale, immediately.

- Hierarchical taxonomy on `wbam-ad`.
- Filter control on All Ads.
- Admin column, positioned next to Placements.
- Bulk enable/disable acting on the filtered set. **No new bulk-action code** -
  `wbam_enable` / `wbam_disable` already act on the selection, so filtering is
  the whole feature.
- Terms cleaned up on uninstall.

Free because organising your own inventory is table stakes, and because a
paywall here makes the plugin worse at its basic job for the sites least able to
manage without it.

### Stage 2 - reporting by group (PRO)

"How did the Sponsors ads perform this month" is the question that turns
organisation into money, and it is where a premium boundary sits honestly.

Analytics already aggregates per ad; grouping by term is a `tax_query` and a
GROUP BY. Belongs in Pro's Analytics module, not Free.

### Stage 3 - delivery by group (design first, FREE engine)

Held. See §6.

## 5. Product constraints stage 1 must meet

These are the difference between a feature that works here and one that works on
every install.

1. **Silent for sites that ignore it.** No behaviour change, no query change, no
   visible difference until a term exists. The 3.0.0 placement gates set the
   precedent - empty means all - and the same instinct applies: adding a
   taxonomy must not alter which ads serve.
2. **Cheap at scale.** The filter runs only on the admin list. Nothing on the
   front end gains a `tax_query` in stage 1; delivery is stage 3, where its cost
   gets designed deliberately rather than inherited.
3. **Capability-correct.** Managing terms is `manage_options`; assigning them is
   `edit_posts`. An editor who can edit ads can file them; only an admin invents
   the filing system. Wrong either way is a support ticket.
4. **Not on `/wp/v2`.** Matches the CPT's existing decision, documented in
   `tests/free/test-cpt.php`: ads are served through `/wbam/v1`, which filters by
   enabled state, and the core route has none of that filtering.
5. **Translatable, and extensible.** All labels through the text domain; the
   registration args through a filter so a site can relabel or add capabilities
   without forking.
6. **Uninstall leaves nothing.** WordPress does not remove terms for a removed
   taxonomy. `uninstall.php` drops six tables today and touches no terms.
7. **Multisite-safe.** Terms are per-site; nothing here is network state.

## 6. Stage 3 - why it is not being built yet

"Ads play based on tags" is two different features and the request does not
distinguish them:

- **Tags scope a slot's candidate pool.** A slot draws only from a group. Lands
  in `Placement_Engine::get_ads_for_placement()`, beside the site and advertiser
  gates from 3.0.0.
- **Tags match the page.** An ad follows content on its subject. Lands in
  `Targeting_Engine::should_display()`, beside the existing inclusion and
  exclusion rules.

Both are legitimate; sites want different ones. Building the wrong one is a
rebuild, and shipping both without deciding is two overlapping targeting systems
- the exact thing 3.0.0 spent its time removing elsewhere in this plugin.

Either lands in **FREE**, following the split already in the code: Free owns the
targeting engine and rule vocabulary, Pro layers rules on through
`wbam_should_display_ad` and `wbam_ad_display_rules`. Pro's entire targeting
module is three additions - pacing, frequency cap, role visibility.

Open questions for that design: precedence against the 3.0.0 gates; whether an
untagged ad matches everything or nothing (3.0.0 chose "empty means all" for
upgrade safety); whether multiple matches affect rotation weight; and how a
tag-skipped ad is surfaced, or "why isn't my ad showing" becomes support load.

## 7. Implementation order

Task-level detail is in `3.1.0-tagging-implementation.md`, which stands except
for the naming change in §3. In short:

1. Register the taxonomy inside `register_post_type()` - same callback as the
   CPT, so registration order cannot drift.
2. Tests first: attached, hierarchical, off `/wp/v2`, **several terms on one
   ad**, capabilities as specified.
3. Filter control, extending the existing `restrict_manage_posts` callback.
4. Prove bulk-by-group needs no new code, by checking untagged ads did **not**
   change state.
5. Column placement, verified at 1440 and 390.
6. Uninstall cleanup.
7. Journey.
8. Manifest, changelog, CLAUDE.md.

## 8. What this deliberately does not do

- Advertisers assigning categories to their own submissions. Categories are the
  site owner's filing of their inventory. Revisit only if asked.
- Categories on the public REST route or the Abilities API - shaped by stage 3.
- Import/export tooling. WordPress's own exporter handles a registered taxonomy.
- Per-term rotation weights. That is a rotation feature wearing a taxonomy
  costume; if it is wanted, it belongs in Pro's Rotation module with its own
  design.
