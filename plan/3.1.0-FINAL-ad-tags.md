# 3.1.0 - ad tags: audited plan, and what to build

Final plan. Supersedes the naming and hierarchy decisions in
`3.1.0-ad-organisation.md`; its problem statement and staging still stand.

## Self-audit of the previous plan

Four claims were checked against the code. Two were wrong, both mine.

### Wrong: `wbam_ad_category`

I recommended "Ad Categories" on the grounds that WordPress users know
categories as hierarchical and multi-assignable.

**"Category" already means two other things in this plugin family:**
`wbam_link_categories` is a custom table in Free's Links module, and
`classified-category` is a real taxonomy in Pro. A third would give a site owner
three unrelated things called Categories in one product.

### Wrong: hierarchical

I chose hierarchy so the taxonomy could be pitched as "folders". Auditing the
reason rather than the conclusion: hierarchy was there to satisfy a *word* in a
client request, not a need most site owners have.

Real inventories group flat - "Sponsor A", "Season 2026", "Leaderboards". Nesting
matters only when someone wants "everything under Practice Area" as a single
action, which is a minority case. Hierarchy costs a checklist-tree metabox and a
parent selector on every term, for all sites, to serve that minority.

And the direction is asymmetric: **flat can become hierarchical later** by
flipping one argument, with terms intact and no migration. Hierarchical cannot be
simplified once site owners have built trees. Start where the reversal is cheap.

Flat also happens to be what the client said, and what WordPress means by "tag".
Choosing hierarchy and calling it "tags" would have taught users something untrue
about it.

### Confirmed: bulk-by-filter needs no new action code - with a caveat I missed

`wbam_enable` / `wbam_disable` act on the selected IDs, so filtering the list is
enough. But **select-all covers the current page only**, and the list paginates
at 20. A site with 100 ads under one tag needs five rounds.

That is a real limit of "filter, select all, apply", and I stated the claim
without it. It is not a blocker - WordPress core has the same behaviour on every
post list - but it must be written down rather than discovered by a site owner
with a large inventory. Screen Options raises per-page, which is the honest
answer for now.

### Confirmed: nothing collides

`wbam_ad_tag` appears nowhere in either plugin. `Placement::get_group()` labels
slots in the picker and is not user-facing vocabulary. Pro's Rotation module
rotates whatever a placement returns. No overlap.

## Decisions

| | |
|---|---|
| Taxonomy | `wbam_ad_tag`, labelled **Ad Tags** |
| Hierarchical | **No.** Flat, reversible upward later |
| REST | Not on `/wp/v2`, matching the CPT |
| Manage terms | `manage_options` - consistent with every other admin gate here |
| Assign terms | `edit_posts` - if you can edit an ad you can file it |
| Where | **FREE**, registered inside `register_post_type()` |

## Build order

1. **Register** in `class-plugin.php::register_post_type()`, after the CPT call.
   Same callback so ordering cannot drift. Args through a filter for relabelling.
2. **Tests** (`tests/free/test-ad-tags.php`), written before the UI:
   attached to `wbam-ad`; flat; off `/wp/v2`; **several tags on one ad**;
   capabilities as decided.
3. **Filter control** on All Ads, extending the existing
   `restrict_manage_posts` callback rather than adding a second listener.
   `hide_empty => false` so a new tag is selectable before anything carries it.
4. **Prove bulk-by-tag**, in the browser: tag three, filter, select all, disable,
   and confirm untagged ads did **not** change.
5. **Column** beside Placements; check 1440 and 390.
6. **Uninstall** removes terms - WordPress does not, and `uninstall.php` drops
   six tables while touching none.
7. **Journey** `admin/03-tag-and-bulk-action-ads.md`.
8. **Manifest, changelog, CLAUDE.md.**

## Out of scope

Delivery by tag (held for the design question in `3.1.0-ad-organisation.md` §6),
reporting by tag (Pro, stage 2), advertisers tagging their own submissions, tags
on the public REST route.
